# App 更新与诊断任务

用户要求加入自动更新、App 日志和性能分析，并明确“不确定的不要做”。本轮先完成无需发布渠道和产品规则决策的本机诊断。原话“自动更新 和个更新”中的后半项含义未确认，不能直接认定为热更新。

## 已实现的本机诊断

| 任务 | 首版实现 | 边界 |
| --- | --- | --- |
| L1 日志文件 | 应用私有目录 `files/diagnostics/app-0.log` 至 `app-2.log`，每份最多 256 KiB，保留最近三份；内存显示最近 80 条 | 旧版 `spike_log.txt` 不继续追加，也不自动导出；不迁移或删除旧日志。 |
| L2 写入开销 | 普通日志在一个后台线程写入；待写队列上限 256，满时丢弃并计数，避免退回主线程写盘 | 未写完就强杀进程时可能丢失少量日志；队列溢出和写入失败可在诊断页看到。 |
| L3 异常记录 | Java 未捕获异常同步尽力保存类型和最多 24 个栈帧，再交给系统原异常处理器 | 不记录异常消息，不吞掉异常或自动放行；不是 native 崩溃 SDK，极端内存不足或磁盘故障不保证写入。 |
| L4 内容与导出 | 日志输出到文件、内存和 logcat 前过滤 URL、常见令牌／口令／绑定码；日志限制单行长度 | 不记录请求／响应正文、答案或应用清单正文。排障日志可能包含前台应用包名，导出前会告知；过滤不能替代不写敏感数据的调用约束。 |
| L5 本机入口 | 长按首页标题进入现有实验台，点击“本机日志与性能”；查看摘要、刷新，手动选择位置导出文本 | 不需要新增存储权限，不接第三方平台，不自动上传。正式家长操作验证仍属于主文档 W3。 |
| P1 资源采样 | 首次约 5 秒、之后每 30 秒，在后台采样本进程 CPU、PSS 和 Java 已用堆 | CPU 为区间增量的单核口径，多核可超过 100%；PSS 不是 Java 堆大小；包含休眠的区间不能当作持续满负载。 |
| P2 主线程与绘制 | 每 30 秒投递一次主线程探针，统计返回延迟及 ≥250ms 次数；记录 Application 初始化到首次 Activity 绘制时间 | 探针是抽样，不能证明无卡顿，也不等同系统 ANR；首次绘制不是完整冷启动 TTID，服务先启动时含等待首屏的时间；不测其他游戏帧率。 |
| P3 接口统计 | 现有统一 HTTP 出口统计各固定路由次数、失败、≥2秒次数、平均／最大耗时 | 从建连到完整读取响应的总耗时，不分 DNS／TLS／服务端执行；不记录 URL、令牌、孩子标识和请求内容。统计故障不能改变网络结果。 |
| P4 退出记录 | Android 11 起启动时读取本应用最近最多 5 条系统退出原因、时刻和内存数值 | 不读取 description 或 trace 正文；系统未留存时不猜测死因，不把主线程探针当作 ANR 判定。 |

新版本为 `0.3-diagnostics`（versionCode 3），保留已实现的游戏模式；没有新增运行时 SDK 依赖、SDK 系统镜像、常驻服务或唤醒锁。资源与主线程采样跟随现有进程，不为诊断单独拉活进程。

## 性能检查结论与验收范围

代码检查已确认旧 `SpikeLog.record` 在调用线程执行无上限 `appendText`，来自首页、无障碍服务等主线程的日志可能等待磁盘。本轮已改为有上限的后台写入。不能据此宣称已测得特定的卡顿降低百分比。

其他需要真实设备数据验证的点：无障碍计时 tick 的规则快照同步 `commit`、用量队列写入、首页每秒应用名称查询。它们涉及持久化与管控正确性，本轮保留行为，不因猜测性能瓶颈改变游戏延期或计时规则。

本轮 Android 76 项测试全部通过（原有 66 项，加 10 项诊断／HTTP 观测检查），Debug APK 构建与 v2 签名校验通过。自动化覆盖日志脱敏及单行限制、轮转上限、重开恢复、并发写入、磁盘失败、限定导出文件与读取大小、CPU 增量及重置、接口计数与实际 HTTP 成败，以及监控回调异常不能影响请求结果。

可选 Android lint 未完成：离线构建缓存缺少 `lint-gradle:31.13.2`，本轮未为此另行下载依赖。不能把 APK 构建或单元测试通过表述为 lint 通过。安装包、SHA-256 及验证范围保存在工作区 `outputs/quizgate-diagnostics-debug.apk` 和 `outputs/日志与性能构建清单.json`，产物不收入源码仓库。

目标手机还需验收：诊断弹窗与文件保存器、崩溃后重启留存、API 26／30 兼容、采样自身开销、真实 CPU／内存基线、长时间游戏中的耗电与卡顿。后续虚拟机已经从本机启动，实际记录了启动、PSS、CPU 和主线程采样；已完成游戏相关界面验证，详见[模拟器游戏验收](模拟器游戏验收.md)。诊断导出和真机性能基线尚未验收。

## 等用户醒来确认的更新问题

| 编号 | 需要确认 | 当前处理 |
| --- | --- | --- |
| U1 | “和个更新”是否指“热更新”，还是手动检查更新／其他含义？ | 不引入动态代码、补丁或热更新 SDK。 |
| U2 | 自动更新具体做到哪一步：自动检查、自动下载后确认，还是要求自动安装？是否有强制更新？ | 没有新增下载、安装、强更和定时联网行为；普通 Android 安装不能直接承诺静默升级。 |
| U3 | 私有 APK 分发还是应用商店？正式 HTTPS 服务地址、更新清单与包的发布位置是什么？ | 沿用现有 Debug 联调；不选择第三方渠道、不发布 APK、不自定生产下载域名。 |
| U4 | 正式发布签名由谁保管，如何备份／轮换？ | 不生成或替换发布私钥；Debug 签名验证仅代表测试包可校验。连续升级需要保持应用 ID 和平台接受的签名关系及版本规则。 |
| U5 | 游戏中、倒计时和答题期间允许提示／下载／安装吗？是否只用 Wi-Fi？ | 不增加中断对局或答题的更新弹窗，不默认使用移动流量下载。 |
| U6 | 日志是否需要家长网页查看、自动上传或接第三方诊断平台？保存多久、谁能看？ | 本轮仅本机查看和用户主动导出；服务端没有新增诊断收集接口。 |

## 更新功能的后续任务（待上述决策明确后实施）

1. 明确 U1—U5，选定 APK／商店路线；若走 Google Play，再评估官方 In-app updates，不能把它当作任意私有 APK 的通用更新器。
2. 定义更新清单：versionCode、versionName、最低系统版本、包大小、HTTPS 地址、校验摘要及发布说明；下载后核对摘要、包名、版本及平台签名关系，失败不得安装。
3. 按确认规则实现检查入口、自动检查间隔、下载进度／重试、安装授权引导；采用系统安装确认流程时清楚展示状态。
4. 避免在游戏或答题关键阶段打断；验证失败重试、拒绝更新、无权限、断网、低存储、旧版本数据和本轮延期次数保留。
5. 用同签名旧／新包实际升级验证，确认服务端兼容，再执行正式发布；未确定前不做强制更新和远程补丁执行。
