# App 更新与诊断任务

用户要求加入自动更新、App 日志和性能分析，并明确“不确定的不要做”。2026-11-09 用户明确：热更新就是“不重新安装修复代码”，先做性能分析和整包更新。本轮 Android 新增性能操作统计及手动检查、下载、校验、系统安装确认入口；实际代码热补丁继续暂缓，正式渠道、签名和自动策略待确认。

## 2026-11-09 本轮实施

- 性能：最近最多 20 个 CPU/PSS/堆样本汇总，固定标签的会话保存、用量写入/确认、首页应用名称查询/刷新及更新操作耗时。首页名称查询增加 32 项、60 秒缓存，回到首页清空；会话保存仍使用同步 commit，保留保存成功后才给延期的语义。
- 整包更新：后台流式下载，大小/SHA-256、包名、versionCode、minSdk 与当前签名集合校验；失败删除半包，重试从头下载，重开页面/进程后重新校验缓存。通过只读私有 ContentProvider 交系统安装器，用户自行授权并确认，不做静默安装。
- 游戏周期、倒计时、答题和持久化的未完成游戏周期暂缓安装；无自动更新弹窗。仅用户手动发起检查/下载，默认正式地址为空；Release 固定构建地址，Debug 可填联调地址。正式 HTTPS 清单和 APK 要求同源且不重定向，当前不支持签名轮换。
- 新增生成清单及 ADB 性能采样脚本，复用已有 SDK；未接第三方运行时 SDK、未选生产下载域名、未生成发布密钥或发布 APK。iOS/鸿蒙暂未接入 Android 更新流程。

详细格式、入口、构建参数和边界见 [Android 性能与整包更新](https://github.com/yaomoshen520/quizgate-android/blob/main/docs/性能与整包更新.md)。本执行环境启动现有 AVD 返回硬件加速不可用，无 ADB 设备；系统安装器、跨版本数据和权限保留、真机性能及采样开销待设备验收。HTTP 单元测试用字节样本验证传输，不替代真实 APK 安装。

本轮验证：104 项 JVM 测试通过；Debug、未签名 Release 构建成功；Release 必要 lint 与两个同签名 Debug 测试包的签名校验通过。完整 Debug lint 仍提示原有 QUERY_ALL_PACKAGES 权限，本轮不删除核心应用清单权限或屏蔽规则，分发渠道及权限审核待确认。默认 Windows 沙盒临时目录限制文件重命名，切换到工作区临时目录后旧写盘测试通过，未修改其持久化语义。

## 实施前的代码评估与后续方向

实施前评估基线：服务端 `c0828e3`、家长端 `f1ff2e3`、Android `3cd457e`。三个 main 分支已快进同步；iOS 与鸿蒙各自跟踪远端平台分支，没有自动将 Android main 合并进去。以下表格保留评估方向，已实施部分以上文为准。

| 方向 | 可直接推进的工作 | 仍需确定/验证 |
| --- | --- | --- |
| 性能分析（优先） | 固定首页、计时、提醒、答题、弱网补报五组场景；记录本进程 CPU/PSS、主线程延迟和接口耗时；增加写盘耗时观测，排查首页每秒查应用名称是否值得缓存，输出优化前后数据 | 模拟器先验证流程和观测开销；真实耗电、厂商后台策略和游戏卡顿需真机。现有首次绘制记录不等于完整冷启动 TTID，主线程抽样也不能判定系统 ANR。 |
| 整包更新（第二） | 可先实现更新清单模型和解析、手动检查入口、下载/失败重试状态、包大小/摘要/包名/版本/签名校验、系统安装确认与重启恢复测试；联调用样本服务，不自选生产下载域名 | 正式分发渠道、HTTPS 地址、发布签名保管、是否自动检查/下载、Wi-Fi 限制、安装时机和是否强更。普通安装不承诺静默升级；真实升级需同一应用身份及平台接受的签名关系。 |
| 配置/内容更新 | 现有家长规则版本下发、联网取题已经不需要重装；可补版本/校验/兼容检查和失败保留旧配置。题目判分继续在服务端，不能借内容更新把远端题的正确答案发给孩子 | 是否需要独立离线资源包、允许更新哪些资源、缓存和过期口径；当前并未实现通用资源更新器。 |
| 原生代码热补丁（后置） | 先列明需要不重装修复的场景、平台范围、补丁签名/适用版本/失败回退要求，再选型 | 需要明确分发渠道和代码补丁是否必要；没有引入动态加载或补丁 SDK，也不能承诺一套补丁同时用于 Android、iOS 和鸿蒙。 |

性能热点已有代码证据：`PrefsSessionStore.save` 的同步 `commit()` 仍由主线程计时链路调用；`MainActivity` 刷新会查询应用名称；用量队列有同步落盘和确认时文件重写。这些是待测量的开销点，并未证明造成了实际卡顿。最新 `SessionTracker` 已处理落盘失败并回滚延期操作，性能改动必须保留“确认保存后才给延期/批准时长”的语义，不能直接用异步 `apply()` 替换。

建议顺序：**性能观测/基线 → 整包更新基础链路 → 配置/内容更新补齐 → 明确必要性后再做原生补丁**。更新提醒和安装应验证游戏、倒计时、答题与待审批阶段，不能随意打断，也不能重置本轮次数。日志上传、网页性能看板仍属于 U6，未新增自动上传。

另一个同步任务：最新共享协议增加了 `HeartbeatReply.device_bound` 和档案/解绑消息，Android 已接入绑定状态；iOS/鸿蒙的协议快照与绑定状态处理需要单独跟进，不能因平台分支 fetch 成功就声称已适配所有新增协议。

## 已实现的本机诊断

| 任务 | 首版实现 | 边界 |
| --- | --- | --- |
| L1 日志文件 | 应用私有目录 `files/diagnostics/app-0.log` 至 `app-2.log`，每份最多 256 KiB，保留最近三份；内存显示最近 80 条 | 旧版 `spike_log.txt` 不继续追加，也不自动导出；不迁移或删除旧日志。 |
| L2 写入开销 | 普通日志在一个后台线程写入；待写队列上限 256，满时丢弃并计数，避免退回主线程写盘 | 未写完就强杀进程时可能丢失少量日志；队列溢出和写入失败可在诊断页看到。 |
| L3 异常记录 | Java 未捕获异常同步尽力保存类型和最多 24 个栈帧，再交给系统原异常处理器 | 不记录异常消息，不吞掉异常或自动放行；不是 native 崩溃 SDK，极端内存不足或磁盘故障不保证写入。 |
| L4 内容与导出 | 日志输出到文件、内存和 logcat 前过滤 URL、常见令牌／口令／绑定码；日志限制单行长度 | 不记录请求／响应正文、答案或应用清单正文。排障日志可能包含前台应用包名，导出前会告知；过滤不能替代不写敏感数据的调用约束。 |
| L5 本机入口 | 长按首页标题进入现有实验台，点击“本机日志与性能”；查看摘要、刷新，手动选择位置导出文本 | 不需要新增存储权限，不接第三方平台，不自动上传。正式家长操作验证仍属于主文档 W3。 |
| P1 资源采样 | 首次约 5 秒、之后每 30 秒，在后台采样本进程 CPU、PSS 和 Java 已用堆 | CPU 为区间增量的单核口径，多核可超过 100%；PSS 不是 Java 堆大小；包含休眠的区间不能当作持续满负载。 |
| P2 主线程与绘制 | 每 30 秒投递一次主线程探针，统计返回延迟及 ≥250ms 次数；记录 Application 初始化到首次 Activity 绘制时间 | 探针是抽样，不能证明无卡顿，也不等同系统 ANR；首次绘制不是完整冷启动 TTID，服务先启动时含等待首屏的时间；不测其他游戏帧率。 |
| P3 接口统计 | 现有统一 HTTP 出口统计各固定路由次数、失败、≥2秒次数、平均／最大耗时 | 从建连到完整读取响应的总耗时，不分 DNS／TLS／服务端执行；不记录 URL、令牌、孩子标识和请求内容。统计故障不能改变网络结果。 |
| P4 退出记录 | Android 11 起启动时读取本应用最近最多 5 条系统退出原因、时刻和内存数值 | 不读取 description 或 trace 正文；系统未留存时不猜测死因，不把主线程探针当作 ANR 判定。 |

新版本为 `0.3-diagnostics`（versionCode 3），保留已实现的游戏模式；没有新增运行时 SDK 依赖、SDK 系统镜像、常驻服务或唤醒锁。资源与主线程采样跟随现有进程，不为诊断单独拉活进程。

## 0.3 首版历史验证

代码检查已确认旧 `SpikeLog.record` 在调用线程执行无上限 `appendText`，来自首页、无障碍服务等主线程的日志可能等待磁盘。本轮已改为有上限的后台写入。不能据此宣称已测得特定的卡顿降低百分比。

其他需要真实设备数据验证的点：无障碍计时 tick 的规则快照同步 `commit`、用量队列写入、首页每秒应用名称查询。它们涉及持久化与管控正确性，本轮保留行为，不因猜测性能瓶颈改变游戏延期或计时规则。

本轮 Android 76 项测试全部通过（原有 66 项，加 10 项诊断／HTTP 观测检查），Debug APK 构建与 v2 签名校验通过。自动化覆盖日志脱敏及单行限制、轮转上限、重开恢复、并发写入、磁盘失败、限定导出文件与读取大小、CPU 增量及重置、接口计数与实际 HTTP 成败，以及监控回调异常不能影响请求结果。

可选 Android lint 未完成：离线构建缓存缺少 `lint-gradle:31.13.2`，本轮未为此另行下载依赖。不能把 APK 构建或单元测试通过表述为 lint 通过。安装包、SHA-256 及验证范围保存在工作区 `outputs/quizgate-diagnostics-debug.apk` 和 `outputs/日志与性能构建清单.json`，产物不收入源码仓库。

目标手机还需验收：诊断弹窗与文件保存器、崩溃后重启留存、API 26／30 兼容、采样自身开销、真实 CPU／内存基线、长时间游戏中的耗电与卡顿。后续虚拟机已经从本机启动，实际记录了启动、PSS、CPU 和主线程采样；已完成游戏相关界面验证，详见[模拟器游戏验收](模拟器游戏验收.md)。诊断导出和真机性能基线尚未验收。

## 更新功能的后续任务

1. 明确 U1—U5，选定 APK／商店路线；若走 Google Play，再评估官方 In-app updates，不能把它当作任意私有 APK 的通用更新器。
2. 本轮已实现清单、下载及校验；正式分发时补签名管理、清单/包发布与服务端兼容验收。
3. 手动检查、进度、重试与授权引导已实现；自动检查间隔及下载策略待确认后再做。
4. 避免在游戏或答题关键阶段打断；验证失败重试、拒绝更新、无权限、断网、低存储、旧版本数据和本轮延期次数保留。
5. 用同签名旧／新包实际升级验证，确认服务端兼容，再执行正式发布；未确定前不做强制更新和远程补丁执行。
