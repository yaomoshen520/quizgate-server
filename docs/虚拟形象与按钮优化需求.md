## 需求一：题库列表"核对通过"按钮文字显示不全

### 现象

家长后台题库列表最右侧操作列，蓝色主按钮文案"核对通过"在列宽不足时被挤成两行，
第二行"通过"被按钮高度裁掉，只剩上半个字；同列下方的"删除"按钮正常。
用户截图见工作区外部附件，此处不入库。

### 必须达到的验收

| 编号 | 判据 | 怎么验 |
| --- | --- | --- |
| B1 | 桌面 1440 宽与 390 × 844 窄屏下，"核对通过"四个字**单行完整显示**，不换行、不被裁切 | 浏览器量按钮 `scrollWidth == clientWidth`，且按钮内文字行数 = 1 |
| B2 | 按钮宽度由文字撑开，不依赖某一列的固定像素宽度 | 人为把该列宽度改小到极端值，按钮仍完整 |
| B3 | 与同列"删除"按钮左右边缘对齐、高度一致，垂直间距不小于 8px | 截图比对 |
| B4 | 主/次按钮的视觉层级不变（核对通过仍是主按钮，删除仍是次按钮） | 现有配色 class 未改动 |
| B5 | 该表格其余列（学科年级、题干、选项、知识点、状态标签）不因此次改动新增截断 | 窄屏整表复测一遍 |

### 约束

- 不改协议、不动 `proto/quizgate.proto`，纯前端展示层修复。
- 不引入新的 UI 组件库，沿用家长后台现有按钮与表格样式。
- 若最终选择"缩短文案"（如改为"通过"）作为手段之一，必须同时保留完整语义的可达途径
  （悬浮提示或状态标签），不能只靠删字解决。
- 全站确认类动作已统一走共用应用内模态窗，本需求不得退回浏览器原生 `confirm`／`alert`。

### 待确认

- C1：文案定为"核对通过"（保持四字，靠样式解决）还是"通过"（改文案）。默认按 B1 保留"核对通过"。

## 需求二：家长给孩子设置虚拟形象，形象随孩子当前行为做动作

### 目标（业务口径）

现在家长后台添加或编辑孩子档案时，只有昵称和年级，孩子端界面上没有任何"这是我"的身份表达。
本需求给每个孩子一个**可爱的虚拟形象**，并且这个形象不是静态头像——孩子正在玩游戏、正在刷短视频、
正在做题时，形象会做对应的简单动作，让孩子端界面认得出"这是我在被管"，也让家长在后台一眼区分多个孩子。

### 家长侧流程

1. 家长在后台"添加孩子"表单，以及孩子档案编辑页，新增一步"选形象"。
2. 形象以网格卡片展示，家长点选一个作为预览和保存结果；不填则用默认形象，不阻断保存。
3. 家长可更换，更换只影响展示，不重置任何闸门规则、用量周期或延期次数。
4. 孩子列表每行在昵称前显示该孩子的形象缩略图，便于多孩子区分。

### 形象与动作

首版做 **6 个可选形象**（动物类，圆润、大眼、无攻击性；具体美术风格待确认），每个形象至少支持
下列 4 个动作状态。动作是"整段小动画循环"，不是逐帧剧情，单段时长 1—3 秒、可循环。

| 状态 | 触发口径 | 动作示意 |
| --- | --- | --- |
| 玩游戏 | 当前前台应用被家长标记为"游戏并监管" | 例如捧着设备晃动、兴奋跳动 |
| 刷短视频 | 当前前台应用属于短视频类（抖音等） | 例如歪头、屏幕反光眨眼的节奏动作 |
| 做题 | 孩子端处于答题界面或闸门抢屏中 | 例如托腮思考、握笔 |
| 空闲 | 以上都不成立 | 待机呼吸、眨眼 |

- 状态来源**必须是已有的数据**：孩子端已有的前台包名探测、家长已有的"游戏与应用"分类、
  以及答题界面自身。**不新增任何采集，不读取应用内文字、截图或对局内容。**
- 短视频类的识别沿用现有分类机制：系统分类 + 家长手工纠正，首版允许把"抖音"等常见包名内置为默认建议。
- 状态切换必须幂等：同一状态重复上报不重播、不抖动；切换动画允许直接切，不要求过渡帧。

### 数据与接口（拟议，未拍板）

- 孩子档案新增一个**形象标识字段**（枚举／短字符串，如 `avatar_id`），存的是"选了哪一只"，
  **不存图片二进制、不存 URL**。动画资源打包在各端本地，服务端只下发标识。
- 添加孩子、编辑孩子的现有接口增加该可选字段；不传即默认值，老客户端不报错。
- 形象标识变更走现有孩子档案更新通道，不新增路由档位。

### 隐私与安全边界（硬约束）

- 不使用孩子真实照片，不提供上传自定义图片（首版明确不做，避免引入文件存储与内容风险）。
- 不新增任何运行时权限、常驻服务或唤醒锁；动画只在界面可见时播放，界面不可见时停掉播放与计时。
- 动画资源不得成为管控绕过面：形象显示与否不能影响闸门强制弹窗和计时逻辑。

### 验收

| 编号 | 判据 |
| --- | --- |
| A1 | 家长能添加孩子时选形象、能改、能在列表里看到缩略图；不选也能成功添加 |
| A2 | 孩子端首页与答题界面显示所选形象；切换形象后孩子端在下次拉取规则时生效 |
| A3 | 四个状态在 Android 11 模拟器上分别实测到：打开 2048 → 玩游戏动作；打开短视频类 → 刷视频动作；进入答题 → 做题动作；回到桌面 → 空闲动作 |
| A4 | 形象动画开启与关闭不影响既有用量上报、延期申请、审批与答题放行链路（现有测试全绿） |
| A5 | 低端机不卡：动画播放时孩子端主线程无明显掉帧，内存无持续增长 |

### 待确认（实现前必须有答复，未答复则保持现状不做）

- C2：美术素材来源——自研／委托／开源可商用素材，三者谁负责产出，何时交付。
- C3：形象数量与风格清单（6 只够不够，是否要人物造型而非动物）。
- C4：动作与状态的映射是否需要家长可配置，还是产品固定。
- C5：iOS 孩子端是否与 Android 同期实现，还是先只做 Android。
- C6：是否显示在家长后台的实时用量页（"孩子此刻在干嘛"），还是只在档案里显示。

## 开源方案候选（**尚未核实，不能据此选型**）

以下是候选方向，**star 数、许可证条款、包体代价、三端 runtime 覆盖都还没实测确认**。
实现前必须先做一次调研并把结论写回本节，尤其要确认免费与商用的边界（是否需要署名、
是否有月活或收入门槛、素材是否允许商用再分发）。

| 方向 | 为什么值得看 | 主要疑虑 |
| --- | --- | --- |
| Rive 官方 runtime（web / android / ios） | 状态机驱动多动作切换正是本需求的形态 | 编辑器与商用授权条款、三端 runtime 成熟度未核 |
| Lottie（lottie-web / lottie-android / lottie-ios） | 生态大、素材站多、三端都有官方库 | 多状态切换要靠多文件或合成，包体与切换成本未量 |
| 精灵图 + Canvas／原生 ImageView | 零第三方依赖、体积可控、低端机友好 | 动作美术要自己逐帧产出，可爱度依赖素材质量 |
| 内联 SVG + CSS 关键帧 | 最轻量，Web 端几乎零成本 | Android/iOS 侧要另找渲染路径，跨端不统一 |
| Live2D Cubism | 二次元"活"感强 | SDK 授权与免费边界最需警惕 |
| 3D（VRM / three-vrm 等） | 表现力最高 | 手机侧体积、性能、低端机风险最大 |
| 现成桌面宠物类开源项目（shimeji／virtual pet 系） | 动作与状态切换的交互设计可参考 | 多为桌面场景，许可证与素材授权逐个查 |

**结论倾向（待验证）**：跨端一致 + 状态机切换 + 包体可控三者权衡下，先看 Rive 与 Lottie 的
三端官方 runtime 与许可证；若两者授权或体积不合适用，退到"精灵图 + 各端原生渲染"这条零依赖路线。
本倾向未经调研证实，不作为实现依据。

1. **P0**：需求一（按钮显示），纯前端，可独立先做先验收。

3. **P2**：需求二的"四态动作"，依赖 P1 字段与素材，且必须先完成开源方案核实与 C2 素材答复。
